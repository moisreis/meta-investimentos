# Overview

This skill defines the rules for naming files, naming code elements, and organizing source code. Follow all rules to keep the codebase consistent, modular, and easy to maintain. Consistent names make the purpose of every file visible at a glance. A stable structure lets developers find code quickly and change it without surprises. For terms, see the glossary in `INDEX.md`.

# Instructions

Apply the rules below in strict order. Follow this sequence when you create or modify any file: Work through the steps in this order each time so naming and placement stay consistent across the codebase.

  - **(1)** File domain
    - Determine the domain that owns the file.
    - Place the file inside that domain's directory.
    - Do not put the file in an unrelated domain directory.
  - **(2)** File responsibility
    - Determine the single responsibility of the file.
    - Keep unrelated concerns in separate files.
    - Select the suffix that matches the responsibility.
  - **(3)** File name
    - Name the file in _kebab-case_.
    - Make the name describe the file's purpose. A reader must infer the responsibility without opening the file.
  - **(4)** Naming conventions
    - Use _SCREAMING_SNAKE_CASE_ for `const` declarations.
    - Use _camelCase_ for all other variables.
    - Use _PascalCase_ for functions.
  - **(5)** File size
    - Keep the file below 250 lines of code.
    - Exclude documentation comments from the count.
    - Split the file when it grows past the limit.
  - **(6)** Separation
    - Extract every additional responsibility.
    - Do not let a file become a **God** file.

# Rules

## File naming

Every **TypeScript** file must use a suffix that clearly identifies its purpose, and every file name must use _kebab-case_. The suffix is not decoration; it tells every reader what role the file plays in the codebase.

Available suffixes include:

  - `*.calculator.ts` for files that represent equations.
  - `*.use-case.ts` for application use cases.
  - `*.value-object.ts` for value objects.
  - `*.entity.ts` for domain entities.
  - `*.event.ts` for domain events.
  - `*.dto.ts` for data transfer objects.
  - `*.interface.ts` for interfaces.
  - `*.id-generator.ts` for identifier generators.
  - `*.repository.ts` for repository definitions.
  - `*.mapper.ts` for row-to-entity mapping functions.
  - `*.query.ts` for read-side queries.
  - `*.job.ts` for background jobs.
  - `*.action.ts` for **Server Actions**.
  - `*.route.ts` for **Route Handlers**.
  - `*.client.ts` for client definitions.
  - `*.schema.ts` for **Drizzle** database schemas.
  - `*.relations.ts` for **Drizzle** database relations.
  - `*.mask.ts` for front-end input masks.
  - `*.presenter.ts` for front-end value presenters.
  - `*.settings.ts` for front-end persisted settings.
  - `*.validation.ts` for input validation schemas.
  - `*.test.ts` for test suites. Never use `*.spec.ts`.
  - `*.dataset.ts` for test dataset factories and fixtures.

`*.schema.ts` is reserved exclusively for **Drizzle** database schemas. Validation schemas never use it; they use `*.validation.ts` instead.

New suffixes may be added as the project introduces new file responsibilities, and each file name must clearly describe its responsibility. Before you add a suffix, confirm that no existing suffix already fits the new kind of file. Every suffix must stay documented so its meaning is unambiguous across the team.

Files generated by the **shadcn/ui** CLI inside `/ui` are the exception to the suffix rule. They keep the names the CLI produces (e.g. `button.tsx`, `dialog.tsx`) and must not be renamed.

**React** component files use the `.tsx` extension and carry no suffix from the list above. Their exports use _PascalCase_ and their hook exports use the `use` prefix, as described under Naming conventions.

**Pattern:**

  `sum-of-values.calculator.ts`

**Anti-pattern:**

  `sumOfValues.ts`

## Test file naming

Unit and integration test files live in `/__tests__/__unit__` and `/__tests__/__integration__`. The test folder mirrors the source path, so the test of a file in `/domain/portfolio/use-cases` lives in `/__tests__/__unit__/domain/portfolio/use-cases`.

The test file name must match the file under test name for name. Use the `*.test.ts` suffix; never use `*.spec.ts`. For a source file `calculate-quotas.use-case.ts`, the test file is `calculate-quotas.use-case.test.ts`.

**Pattern:**

  `calculate-quotas.use-case.ts` -> `calculate-quotas.use-case.test.ts`

**Anti-pattern:**

  `calculate-quotas.spec.ts`

## Naming conventions

Every `const` declaration must use _SCREAMING_SNAKE_CASE_. All other variables must use _camelCase_. Functions must use _PascalCase_. The casing reveals the role of each name in the code, so a reader can tell constants, variables, and functions apart just by how they are written.

Custom **React** hooks are the exception to the function rule. A custom hook must use _camelCase_ and must be prefixed with `use`. This prefix is a hard **React** requirement, not a style choice. Example: `usePortfolio`.

File names and code names follow different rules. A file name must always use _kebab-case_. When that file exports a **React** component, the export must use _PascalCase_ while the file name stays _kebab-case_. Example: the file `form-tools.tsx` exports `FormTools`. Do not create a file named `FormTools.tsx`.

**Examples:**

  ```typescript
  const MAX_RETRIES = 5;

  let retryCount = 0;

  function CalculateTotal(): number {
    return retryCount;
  }
  ```

Do not use _camelCase_ for `const` declarations.

**Anti-pattern:**

  ```typescript
  const maxRetries = 5;
  ```

Do not use _SCREAMING_SNAKE_CASE_ for functions or mutable variables.

**Anti-pattern:**

  ```typescript
  function CALCULATE_TOTAL(): number {
    return 100;
  }

  let RETRY_COUNT = 0;
  ```

## Single responsibility

Every file must follow the *Single Responsibility Principle* by containing one clear responsibility and avoiding unrelated concerns. For example, a use case must not also define database schemas, HTTP clients, validation logic, or presentation logic. When responsibilities must be separated, each responsibility must have its own file. A focused file is easier to read, test, and refactor than a file that quietly handles several jobs at once.

**Pattern:**

  ```text
  calculate-quotas.use-case.ts
  quota.repository.ts
  quota.schema.ts
  quota.presenter.ts
  ```

**Anti-pattern:**

  ```text
  quota.ts
  ```

The `quota.ts` file must not contain all application, domain, database, and presentation logic. When you notice a file doing more than one job, split it before it becomes hard to change.

## File size

  - Files must remain small and focused.
  - A file must not exceed 250 lines of code, excluding documentation comments.
  - Documentation comments do not count toward the 250-line limit.
  - When a file grows beyond 250 lines, split the file into smaller modules with clear responsibilities.
  - Do not keep adding code to a file only to avoid creating new modules.

**Anti-pattern:**

  ```text
  large-module.ts
  ```

The file contains multiple responsibilities and exceeds the 250-line limit.

**Pattern:**

  ```text
  calculate-quotas.use-case.ts
  validate-quota.use-case.ts
  quota.repository.ts
  quota.presenter.ts
  ```

Each file contains one focused responsibility. Splitting a large file into single-purpose modules keeps the codebase maintainable as the project grows.

## Line length

Every code and documentation line must stay within 65 characters. Documentation prose in markdown files is excluded from this limit. JSX markup lines in `.tsx` files are also exempt from this limit. Break long lines manually at a natural boundary to keep the text readable.

## God files

God files are forbidden. A God file is a file that manages multiple responsibilities, dependencies, functions, classes, or unrelated business rules. When a file begins to manage multiple concerns, extract each concern into a dedicated file. Common concerns that must be separated include:

  - Business rules.
  - Database access.
  - Validation.
  - HTTP communication.
  - Data transformation.
  - Presentation.
  - Authentication.
  - Authorization.
  - Background processing.

The goal is to keep each module focused on one responsibility. A module stays healthy when it can be understood entirely on its own. Review files during code review to catch **God** files before they grow.

## Directory structure

  - Files must live inside a directory that represents their domain and responsibility.
  - A file must not be placed in an unrelated domain directory.
  - The directory structure must reflect the purpose of the file.

**Pattern:**

  ```text
  portfolio/
  └── use-cases/
      └── calculate-quotas.use-case.ts
  ```

**Anti-pattern:**

  ```text
  user/
  └── hooks/
      └── calculate-quotas.use-case.ts
  ```

The `calculate-quotas.use-case.ts` file belongs to the portfolio domain and must not live inside the user domain. A reader must be able to trust that the folder tells where the file belongs.

## Domain organization

Each domain must own the files that implement its behavior. Keep domain-specific files inside that domain's directory. Do not move a file into a generic directory only because it is used by more than one module. When shared behavior is required, create an explicit shared module with a clear responsibility. Shared code earns a place only when it has one clear job and is owned explicitly.

**Pattern:**

  ```text
  portfolio/
  ├── entities/
  ├── use-cases/
  ├── interfaces/
  ├── events/
  └── calculators/
  ```

**Anti-pattern:**

  ```text
  utils/
  ├── portfolio.ts
  ├── user.ts
  ├── payment.ts
  └── authentication.ts
  ```

Generic directories must not become containers for unrelated business logic. If shared code appears, extract it into an explicit module instead of dumping it into a generic folder.

## Suffix and directory consistency

The file suffix and directory must describe the same responsibility. A file must not use a suffix that conflicts with its location or implementation. A mismatch confuses readers about where to look and what to expect from the file.

**Pattern:**

  ```text
  portfolio/
  └── use-cases/
      └── calculate-quotas.use-case.ts
  ```

**Anti-pattern:**

  ```text
  portfolio/
  └── repositories/
      └── calculate-quotas.use-case.ts
  ```

The suffix and directory must communicate the same purpose. When they disagree, choose the one that matches the real responsibility and rename the other.

## Naming and responsibility

Names must describe what the code does. A good name explains the file's job without requiring comments. Prefer precise names that come from the domain over vague ones.

Avoid generic names such as:

  - `helpers.ts`
  - `utils.ts`
  - `common.ts`
  - `manager.ts`
  - `service.ts`
  - `data.ts`
  - `misc.ts`

Use names that describe the actual responsibility.

**Pattern:**

  `format-currency.presenter.ts`

**Anti-pattern:**

  `utils.ts`

## Refactoring rule

When a file starts to contain multiple responsibilities, extract the responsibilities into separate files. When a file exceeds 250 lines of code, refactor it before adding new functionality. When a new responsibility is added, first determine whether it belongs in the current file. If it does not belong to the current responsibility, create a new file with the correct suffix. Refactoring is part of normal work, not a separate cleanup phase. Keep the codebase tidy at every step so modules never degrade silently.

# Anti-patterns

Do not violate any of the following rules when writing code:

* **Do not use _PascalCase_ or _camelCase_ for file names.**
* **Do not name a file after its _PascalCase_ component export.**
* **Do not create TypeScript files without a suffix.**
* **Do not violate the shadcn-generated file names inside `/ui`.**
* **Do not use `*.spec.ts` for test files.**
* **Do not name a test file without a 1:1 match to the file under test.**
* **Do not use _camelCase_ for `const` declarations.**
* **Do not use _SCREAMING_SNAKE_CASE_ for functions.**
* **Do not use _PascalCase_ for custom **React** hooks.**
* **Do not name custom **React** hooks without the `use` prefix.**
* **Do not use _SCREAMING_SNAKE_CASE_ for mutable variables.**
* **Do not use `*.schema.ts` for validation schemas.**
* **Do not place unrelated responsibilities in one file.**
* **Do not create God files.**
* **Do not exceed 250 lines of code excluding documentation.**
* **Do not place files inside unrelated domain directories.**
* **Do not use generic files as containers for unrelated logic.**
* **Do not use a suffix that conflicts with the file responsibility.**
* **Do not add new logic to an oversized file before refactoring it.**
* **Do not exceed 65 characters per code or documentation line.**
